# Specification — To Do App

## 1. Overview

Web application for managing tasks through a single page. The user can add tasks, view the current task list, and remove tasks from the browser.

The front end will be implemented with HTML, CSS, and browser JavaScript. The back end will be implemented with Node.js, providing the HTTP API and serving the application’s static files. Data will be stored only in memory and will be lost when the server restarts.

## 2. Scope

### Included

- Task list visualization.
- Adding one task at a time.
- Removing an existing task.
- Required-title validation.
- Unique task identification.
- In-memory storage in the Node.js process.

### Out of scope

- Login and user management.
- Database or file persistence.
- Task editing.
- Marking tasks as completed.
- Categories, filters, or configurable sorting.

## 3. Functional requirements

### FR-01 — Display tasks

When the page is opened, the system must request the back end and display all tasks stored in memory. If there are no tasks, it must display an empty-list message.

### FR-02 — Add a task

The user must enter a title in the text field and select the **Add** button. The system must:

1. Remove leading and trailing whitespace from the submitted value.
2. Reject values that are empty after normalization.
3. Create a task with `id`, `tittle`, and `ratedAt`.
4. Store the task in memory.
5. Update the list displayed in the browser.
6. Clear the text field after a successful operation.

### FR-03 — Remove a task

Each list item must have a **Remove** button. When selected, the front end must request removal using the task `id` and, if successful, remove the item from the list.

### FR-04 — Error handling

The front end must inform the user when:

- the title is empty;
- communication with the back end fails;
- the task cannot be found for removal.

## 4. Data model

Each task must follow the contract below:

```json
{
  "id": "a1b2c3d4",
  "tittle": "Study Node.js",
  "ratedAt": "2026-10-14T15:30:00.000Z"
}
```

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | string | Yes | Unique task identifier generated by the server. |
| `tittle` | string | Yes | Task title. The name `tittle` must be retained as provided in the requirement. |
| `ratedAt` | ISO 8601 string | Yes | Task creation date and time. |

## 5. Back-end API

### `GET /api/tasks`

Returns all stored tasks.

`200 OK` response:

```json
{
  "tasks": [
    {
      "id": "a1b2c3d4",
      "tittle": "Study Node.js",
      "ratedAt": "2026-10-14T15:30:00.000Z"
    }
  ]
}
```

### `POST /api/tasks`

Creates a task.

Request:

```json
{
  "tittle": "Study Node.js"
}
```

`201 Created` response: returns the created task using the same data model format.

`400 Bad Request` response when `tittle` is missing, is not a string, or is empty after whitespace is removed:

```json
{
  "error": "The task title cannot be empty."
}
```

### `DELETE /api/tasks/:id`

Removes the task identified by `id`.

`204 No Content` response when the removal succeeds.

`404 Not Found` response when no task exists with the provided `id`:

```json
{
  "error": "Task not found."
}
```

## 6. Front-end requirements

- There must be a single HTML page.
- The page must contain a text field, an **Add** button, and a task list.
- Each task must display its title and a **Remove** button.
- API communication must use `fetch`.
- The page must not reload when adding or removing a task.
- The field must support submission with the Enter key.
- The title must be inserted into the DOM safely, without interpreting user-provided content as HTML.
- Buttons must have accessible text or labels.

## 7. Back-end requirements

- Node.js must serve the front-end static files.
- The API must respond with JSON, except for `204` responses.
- The back end must set appropriate content headers.
- Storage must use an in-memory structure, such as an array or `Map`.
- The `id` must be generated by the server and must not depend on a value sent by the client.
- `ratedAt` must be generated by the server when the task is created.
- The server must return HTTP status codes appropriate to the operation result.

## 8. Main flow

1. The user opens the page.
2. The front end calls `GET /api/tasks`.
3. The user enters a task and selects **Add**.
4. The front end sends `POST /api/tasks`.
5. The server validates, creates, and returns the task.
6. The front end adds the task to the list.
7. The user selects **Remove**.
8. The front end sends `DELETE /api/tasks/:id` and removes the item after receiving `204`.

## 9. Acceptance criteria

- [ ] When the page opens, the task list is loaded through the API.
- [ ] A task with a non-empty title is created and appears in the list.
- [ ] Titles containing only whitespace are rejected.
- [ ] A created task has `id`, `tittle`, and `ratedAt`.
- [ ] Each task has a functional button to remove it.
- [ ] A removed task no longer appears in the list.
- [ ] Attempting to remove a nonexistent `id` returns `404`.
- [ ] Data remains available while the server is running.
- [ ] Data is lost after the server restarts, as defined for in-memory storage.
- [ ] The application works without reloading the page during addition and removal.

